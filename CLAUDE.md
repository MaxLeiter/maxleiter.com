# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `pnpm dev` — watch, rebuild, serve on localhost:3000 with live reload (`framework/dev.ts`, the only file allowed to use `Bun.*`). No Fast Refresh: an edit reloads the page.
- `pnpm build` — the production build under Node (`node scripts/build.mjs`). This is what Vercel runs.
- `pnpm build:bun` — the same build under Bun (`bun run build.ts`). Faster locally; byte-identical output.
- `pnpm check` — `tsc --noEmit`.
- `pnpm lint` — `oxlint .` then `oxfmt --write`. Must exit 0.
- `pnpm gate` — build, snapshot the output, diff it against the committed parity baseline. Must report `blocking: 0` and `route issues: 0`.
- `pnpm snapshot` / `pnpm verify` — the two halves of `gate`, run separately.

Package manager is pnpm 9.15.9. Node 24 (`engines`) or Bun both work; nothing in
the build path uses a runtime-specific API.

### Content

- Blog posts: MDX files in `/posts/`. Notes: MDX files in `/notes/`. Frontmatter drives everything; `published: false` excludes a file.
- External posts and project data live in `framework/content.ts`. The pinned popular posts live in `app/lib/popular-posts.ts`, and where a post or note lives is `entryHref` in `app/lib/blog-post.ts` — both are leaf modules because the desktop island imports them and cannot reach anything that imports `node:fs`.
- The feed, sitemap, robots.txt and search index are generated by `framework/feeds.ts`. There is no separate RSS script.

## Architecture

A bespoke static site generator. There is no web framework dependency and no
server: every route is rendered to HTML at build time and served as a static
file.

### Build pipeline (`build.ts` orchestrates)

1. `framework/content.ts` — reads `posts/`, `notes/` and project data with gray-matter into a `BuildContext`.
2. `framework/entry-server.ts` — esbuild bundles this (and through it `framework/routes.ts` and every page) to `.cache/server/entry.mjs`, then `build.ts` imports it. Path aliases, CSS modules and JSX are all resolved by esbuild, once, which is why Bun and Node produce the same bytes.
3. `framework/mdx.ts` + `framework/highlight.ts` — `@mdx-js/mdx` compile and run, with remark-frontmatter, remark-gfm, remark-a11y-emoji, remark-toc, rehype-slug, rehype-autolink-headings, and Shiki dual-theme highlighting emitted as CSS custom properties (zero client JS, switched by `[data-theme]`). Content-hashed cache in `.cache/`.
4. `framework/render.tsx` — `renderToStaticMarkup` into the HTML shell: `<head>`, inlined CSS, the blocking theme script, island bootstrap JSON.
5. `framework/css.ts` — Tailwind 4 CLI over `app/styles/global.css` plus the collected CSS-module output, minified into one base sheet inlined into every page. Every CSS module is then its own conditional fragment, keyed by the scoped class names lightningcss returns for it, and added only to pages whose markup (including island `data-props` JSON) mentions one of them. There is no list of "feature" modules to maintain; `build.ts` verifies each module's rules are anchored to its own classes and falls back to the base sheet, loudly, when they are not.
6. `framework/client.ts` — esbuild per island plus the runtime, `react`/`react-dom` aliased to `preact/compat`, code-split and hashed into `/_assets/`.
7. `framework/platform.ts` — OG images, feeds and the Vercel config, run concurrently because they write disjoint files. A failure here is fatal, deliberately: a build with no feed and no config.json would otherwise exit zero. Fonts are prepared once by `build.ts` itself, before any page is written, because the shell needs their `@font-face` CSS; the result is passed in so the platform log can report it.
8. `build.ts` also writes `.vercel/output/routes.json`, the manifest of every document it emitted. The sitemap derives its top-level pages from it, so adding a route to `framework/routes.ts` cannot silently miss the sitemap.

### Islands

Pages are plain React rendered to static markup. Anything interactive is an
island: `<Island name="x" on="idle" props={...}>` (see `framework/islands.tsx`)
emits a `data-island` wrapper around server-rendered fallback markup, and
`framework/client/runtime.ts` (~2 KB, framework-free) hydrates it with Preact on
`load` / `idle` / `visible` / `interaction`.

- Island sources live in `app/islands/<name>.tsx` with a default export, and must render markup identical to their fallback on first render.
- **Islands take class names as props, never by importing a CSS module.** The client esbuild config deliberately has no `*.module.css` plugin so that violating this fails loudly instead of shipping a second copy of rules already inlined in the page.
- The runtime also owns, with no island: the theme toggle, Cmd/Ctrl+K, delegated `[data-track]` analytics, and `pageswap` view-transition naming. It is the single owner of that last one — elements opt in with `data-vt-name`, and it names at most one of them. The menubar clock is NOT the runtime's: it exists only on the homepage, where the desktop island hydrates over it and owns it.
- Instant navigation is chosen by capability detection, never by user-agent sniffing (there is no `navigator.userAgent`/`platform`/`vendor` anywhere in `framework/` or `app/`). Where `HTMLScriptElement.supports('speculationrules')` and `PageRevealEvent` both exist (Chrome, Edge), pages rely on the `<script type="speculationrules">` prerender hints plus `@view-transition` and the JS router is never downloaded; everywhere else `runtime.ts` lazily `import()`s the router, so it stays a separate chunk.
- The runtime also intercepts same-origin `<a>` clicks and navigates in the same document (`framework/client/router.ts`), so the browser never shows its loading indicator. It only handles primary-button, modifier-free, same-origin links with no `target`/`download`/`rel=external`, that are not pure hash changes and not inside `[data-no-router]`; everything else stays a real navigation, which is what keeps cmd-click and middle-click native. Every route is emitted twice — `index.html` and `index.partial.html` beside it, carrying only the title, per-page meta, that route's CSS fragments, the island JSON and the body — and the router fetches the partial, falling back to the full page. That is why the inlined sheet is two tags, `#css-base` (identical site-wide, never touched) and `#css-page` (swapped per route). Islands are unmounted before the body is replaced, so the generated hydrate wrapper returns its own `root.unmount()`. Prefetch runs on hover, on `pointerdown` and on links entering the viewport, through one promise-keyed cache so a click consumes the in-flight request.
- `on="visible"` islands share one `IntersectionObserver` and are observed directly, never through a parent. A zero-area island still mounts — per spec a target intersects when it merely touches the root, "even if the intersection has zero area" — which is what lets the shot grid render only a `<dialog>` as a sibling of the server-rendered grid rather than wrapping markup it cannot reproduce. A real fallback is still preferred: it is what makes the page work with JavaScript off.

### Layout

```
build.ts                     the whole build
framework/                   content, mdx, highlight, render, css, client, islands,
                             routes, platform (og/feeds/vercel/images/fonts), dev
framework/routing.ts         URL → file: redirects, the ?embed rewrite, content
                             types. config.json, the dev server and the harness
                             all read this one table
framework/transitions.ts     transitionName(kind, slug) and its URL inverse
framework/client/runtime.ts  the client runtime
app/pages/                   page components (plain React)
app/islands/                 client islands
app/components/              shared components, server-rendered
app/mdx/                     MDX component maps: static-components + island-components
app/styles/                  global.css, markdown.css, CSS modules
tools/                       snapshot + HTML diff harness
docs/rewrite/                design docs, and baseline/ the committed parity baseline
```

### Platform

Output is the Vercel Build Output API: `.vercel/output/static/**` plus
`.vercel/output/config.json` (redirects, embed rewrites, immutable `_assets`
headers, the 404 error route, and the `images` block that enables
`/_vercel/image`) and `.vercel/output/routes.json` (the build's own route
manifest, outside `static/` so it is never served). The routing rules in
`config.json` are generated from `framework/routing.ts`, which the dev server
and the snapshot harness interpret too, so the three cannot drift.
`framework/vercel.ts` also writes the root `vercel.json`, so change it there
rather than by hand — a build overwrites the file.

`vercel.json` pins `framework: null`, an explicit `npx --yes pnpm@9.15.9 install
--frozen-lockfile --prod=false`, and `node scripts/build.mjs`. All three
override the project dashboard per deployment. `--prod=false` is load-bearing:
the site is static output, so every build dependency sits in `devDependencies`,
which pnpm would skip under `NODE_ENV=production`.

### Parity harness

`tools/snapshot.ts` normalizes rendered output (hashes, timestamps, attribute
order) into a per-route snapshot; `tools/diff-html.ts` diffs it against
`docs/rewrite/baseline/`. The blocking streams are `head`, `prose`, `code` and
`file`; the raw `html` and `text` diffs are printed but never fatal. To accept
an intended change, regenerate the baseline with `bun run tools/snapshot.ts
--out docs/rewrite/baseline --raw .cache/baseline-raw` and say why in the commit.

**Adding a post or a note does not fail the gate.** Routes the build's own
`.vercel/output/routes.json` declares but the baseline does not contain are
reported as `added routes: N` and listed. Re-snapshot the baseline with
`pnpm snapshot --dir .vercel/output/static --out docs/rewrite/baseline` only
when you actually intend to re-baseline. Two cases stay fatal: a route the
baseline has and the build no longer emits, and an `index.html` in the output
that the route manifest never declared, which means something is writing pages
the registry does not know about.

### Environment variables

None. The build makes no network requests and reads no secrets. `GITHUB_TOKEN`
was only used for a project-star fetch whose result was discarded before render;
it is gone. `PORT` overrides the dev server's 3000.

## Code Conventions

- **TypeScript**: strict, no `any`.
- **Formatting**: no semicolons, single quotes, 2-space indent, 80 cols (oxfmt).
- **Imports**: extension-less everywhere under `app/` and `framework/`; path alias `@*` → `./app/*`. `tools/` runs unbundled and may use `.ts` extensions.
- **CSS**: Tailwind utilities first, CSS modules for component-scoped rules. `build.ts` generates a `.d.ts` beside every `*.module.css`, so those are build output — do not hand-edit them.
- **Content files**: YAML frontmatter with `title`, `date`, `description`.
