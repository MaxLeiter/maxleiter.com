## 1. ROUTES

### 1.1 Global rendering posture

`app/layout.tsx:12` declares `export const dynamic = 'force-static'`. As a root-layout segment config this cascades to **every page segment**, so the entire page tree is prerendered at build. There is no `middleware.ts` / `proxy.ts`, no `loading.tsx`, no `not-found.tsx`, no `template.tsx`, no `default.tsx`. The only special file is `app/error.tsx`.

### 1.4 API routes

**`app/api/search-index/route.ts`** — `export const dynamic = 'force-static'` (`:10`). Prerendered to a static JSON file at build. `GET` builds a flat array of `{type, title, href, external}` from `getBlogPosts()` + `getProjectsData()`. Called by `loadSearchIndex()` in `app/components/desktop/command-palette.tsx:38` via `fetch('/api/search-index')`, once per page load, lazily on first ⌘K. This is a deliberate optimization to keep the post list out of every page's RSC payload. **A replacement can emit this as a plain `search-index.json` file — zero server needed.**

**`app/api/knightos-package/[...path]/route.ts`** — no segment config, so it is a **dynamic serverless function**. Proxies `GET https://packages.knightos.org/<path>` and re-serves the bytes as `application/octet-stream` with `Cache-Control: public, max-age=31536000, immutable`. **Nothing in the repo calls it.** `public/knightos/main.js:101` and `main.coffee:73` XHR `https://packages.knightos.org/...` *directly*, bypassing the proxy. This route is dead code — it is the only genuinely dynamic server endpoint in the app, and it can be deleted.

### 1.5 Redirects (`next.config.mjs`, all `permanent: true` → 308)

- `/X11` → `/blog/X11`
- `/atom` → `/feed.xml`
- `/feed` → `/feed.xml`
- `/rss` → `/feed.xml`

On Vercel these compile into the platform routing layer, so a replacement can ship an equivalent `vercel.json` `redirects` block with no code.

### 1.6 Bottom line on server requirement

**Nothing on this site needs a server at request time.** The one dynamic route is unreferenced. Every data source (filesystem, GitHub API, `raw.githubusercontent.com`) is consumed at build time. Analytics is a client-side beacon to Vercel's endpoint.

### The `<ViewTransition>` landmine

`app/components/page-transition.tsx:3` and `app/components/view-transition-wrapper.tsx:3` do `import { ViewTransition } from 'react'`. **The installed `react@19.2.8` does not export `ViewTransition`** — verified: `'ViewTransition' in require('react') === false`. It only resolves because Next aliases the bare `react` specifier to its own vendored copy, `next/dist/compiled/react`, which *does* export it (`node_modules/next/dist/compiled/react/cjs/react.react-server.development.js:596`).

Consequences for a replacement:
- You must either vendor `react-experimental` yourself, alias `react` the same way Next does, or drop `<ViewTransition>` and drive `document.startViewTransition()` by hand.
- There is a memory note on this already: the page-level transition boundary lives in the root layout, and browser back/forward (popstate) can never animate.

### 3.2 Libraries that hard-require the async-RSC runtime

**`bright@1.0.0`** — `app/mdx/components/index.tsx:6` imports `{ Code }` and maps it onto `pre` (`:61`). Verified async: `node_modules/bright/dist/index.js:234` is `async function BrightCode(props)`, `:239` `async function highlight(props)`, and `:379` does `import "server-only"`. It depends on `@code-hike/lighter` (a TextMate/Shiki-family highlighter). Theme configured at `index.tsx:30-34`: dark `solarized-dark`, light `material-palenight`, switched by `lightSelector: '[data-theme="light"]'` — i.e. **both themes are rendered into the HTML** and CSS picks one, so there is no flash and no client JS.
*Without RSC:* highlight at build time with `shiki` (`codeToHtml` with `themes: {light, dark}` and `defaultColor:false`, which produces exactly this dual-theme CSS-variable output). Straightforward — arguably better, since Bright 1.0.0 is unmaintained.

**`react-tweet@3.3.1`** — `app/mdx/components/tweet-block.tsx:1` and `app/mdx/components/tweet-thread.tsx:1` import `{ Tweet }`. Package `exports` has a `"react-server"` condition (`node_modules/react-tweet/package.json:19-22`) → in an RSC graph this resolves to `dist/index.js`, the **async server** variant that fetches the tweet at render time. Neither file has `'use client'`, so **the RSC variant is what's in use**; no SWR, no client fetch.
*Without RSC:* call `getTweet(id)` from `react-tweet/api` at build time and render the presentational components from `react-tweet/dist/twitter-theme/*` with the resulting data. `<TweetThread>` is registered in the MDX map (`index.tsx:23`, `:91`) but **is used by zero posts** — only one post uses `<Tweet>`.

**`next-mdx-remote@6.0.0`** — `app/mdx/post-body.tsx:1` imports `MDXRemote` from `next-mdx-remote/rsc`, the async server-component variant that compiles MDX **at render time on every page render** (which, because everything is force-static, means once per page at build). Its real dependency is `@mdx-js/mdx@^3`.
*Without RSC:* call `@mdx-js/mdx`'s `compile()` at build time directly. This is the single biggest performance lever available — the current pipeline re-runs the full unified/remark/rehype stack per page during the build, inside the RSC renderer.

**`react-diff-viewer@3.1.1`** — client-only (`mdx-diff.tsx:1` has `'use client'`), loaded with `ssr:false` (`mdx-diff-lazy.tsx:10`). Pulls in emotion (~48KB per the comment at `mdx-diff-lazy.tsx:5`). Used by 3 posts. No RSC dependency.

### 3.3 What breaks without an RSC runtime

Nothing user-visible, *if* the build does the work eagerly. Every RSC use here is "run this async thing once at build and inline the HTML" — none of it is per-request. The three async server components (`Code`, `Tweet`, `MDXRemote`) plus the filesystem-walking `MinecraftInventoryFromDir` map cleanly onto a build-time MDX compiler with async plugins.

The genuine losses are:
1. `next/dynamic` on server components (`index.tsx:22-28`) — the mechanism for keeping a heavy component's *client* children and CSS out of posts that don't use it. A per-post bundle graph replaces this.
2. RSC payload streaming for soft navigation — see §4.

## 4. CLIENT-SIDE INTERACTIVITY SURFACE

### 4.1 What hydrates on every page

`app/layout.tsx:74-83` mounts, on **every route**:
- `ThemeProvider` (next-themes, `attribute="data-theme"`, `defaultTheme="dark"`, `enableSystem`) — injects a blocking inline script into `<head>` to set `data-theme` before paint. `<html suppressHydrationWarning>` at `:71`.
- `EffectsProvider` (`effects-context.tsx:20`) — a single boolean, `showCommandPalette`.
- `PageTransition` (`page-transition.tsx:13`) — the persistent `<ViewTransition>` boundary. Must live above the router outlet, per the comment at `:8-12`.
- `GlobalKeyboardHandler` (`global-keyboard-handler.tsx:15`) — ⌘K/Ctrl+K listener. The palette itself is `next/dynamic({ssr:false})`, so nothing ships until first open.
- `Analytics` from `@vercel/analytics/react`.

So the baseline hydration cost on a blog post is: theme provider, effects context, view-transition boundary, keyboard listener, analytics, plus `WindowToolbar` (`blog-post-page-client.tsx:44`) which is a client component holding a `useRouter`.

### 4.2 The desktop (`/` only)

`desktop-client.tsx` (779 lines) is the whole homepage. Client-side because it manages window state.

- **Window manager** — `useReducer` at `:399` over `{openWindows: Set<WindowId>, blogPostSlug, focusedWindow, zIndexes, nextZIndex}`. Initial `nextZIndex` 50. Actions: `OPEN_WINDOW`, `CLOSE_WINDOW`, `OPEN_BLOG_POST`, `CLOSE_BLOG_POST`, `FOCUS`.
- **`Window`** (`window.tsx`, 504 lines) — drag via `.window-header` with mouse *and* touch handlers, corner resize (min 300×200), viewport clamping on mount (`:38-53`), auto-fullscreen under 768px (`:83-88`), and **edge snapping** with a 20px threshold and a live preview overlay (`:330-388`): left/right halves, top = fullscreen, bottom half. Pre-snap geometry is saved and restored when you drag a snapped window off an edge (`:141-151`).
- **Maximize is navigation, not a resize.** `toggleFullscreen` (`:203-225`): if the window is a blog post, `router.push(postHref)`; if it's a content window, `router.push('/'+pageType)`; only a plain window actually toggles local fullscreen state.
- **Blog posts render in an `<iframe>`.** `desktop-client.tsx:694-698` mounts `<iframe src={href + '?embed=true'}>` inside the window, wrapped in `<ViewTransition name={'blog-post-'+slug}>`.
- **Hover preloading via hidden iframe** — `:653-659` mounts a `className="hidden"` iframe for the hovered post, cleared after a 1s timeout (`:477-479`).
- **The `?embed=true` handshake.** `blog/[slug]/page.tsx:11-35` and `notes/[slug]/page.tsx:11-31` inject a blocking inline `<script>` that reads `?embed`, sets `window.__IS_EMBED__`, and **physically `.remove()`s `#blog-toolbar` from the DOM** before React hydrates, so the client component's `useState(() => window.__IS_EMBED__)` initializer (`blog-post-page-client.tsx:28-34`) matches. A hand-rolled hydration workaround.
- **Clock** — `(subpages)/page.tsx:5-27` injects an inline script that writes `toLocaleTimeString` into `#menubar-clock` and stashes it on `window.__INITIAL_TIME__`; `desktop-client.tsx:408-428` seeds `useState` from that global and re-ticks every 60s. Another hand-rolled hydration workaround.
- **`?openPost=<slug>` deep link** — `:435-444`: on mount, opens that post's window and `history.replaceState({}, '', '/')`. This is how "minimize" round-trips: `blog-post-page-client.tsx:37` does `router.push('/?openPost='+slug)`.
- **Mobile divergence** — `useIsMobile()` (`use-is-mobile.ts`, `useSyncExternalStore` on `resize`, `<768px`, server snapshot `false`). Under 768px, clicking a folder or post **navigates** instead of opening a window (`:278-284`, `:449-455`).
- **Ctrl+W** closes the focused window (`:527-545`). Cmd+W is deliberately avoided.
- **Calculator** — `next/dynamic({ssr:false})` at `:39`. `calculator.tsx` loads RequireJS from `/knightos/require.min.js`, configures `baseUrl:'/knightos'`, fetches `/knightos/KnightOS-TI84pSE.rom` as an ArrayBuffer, and boots a z80 emulator into a `<canvas>` with an on-screen keypad. Entirely static assets under `public/knightos/`.
- **Widgets** — `WidgetRecentPosts` (popular slugs from `app/lib/popular-posts.ts` = `['weights','xios','formatting']`, then 3 recent) and `WidgetTopProjects` (top 5). Both are `'use client'` **solely** to call `track()` from `@vercel/analytics` and to take the `onPostClick` callbacks.
- **Analytics events** — `track('nav_click', {section})` at `desktop-client.tsx:277`; `track('blog_click', {slug})` at `:448`; `track('nav_click', {section, source:'widget'})` at `widget-recent-posts.tsx:131` and `widget-top-projects.tsx:108`; `track('project_click', {project})` at `widget-top-projects.tsx:73`.

### 4.3 Command palette

`command-palette.tsx` — ⌘K/Ctrl+K anywhere (`global-keyboard-handler.tsx:21`) or the header search button (`desktop-client.tsx:616`). Three hardcoded nav items plus the fetched index. Filtering is a naive `title.toLowerCase().includes(query)` (`:70`) — no fuzzy matching, no ranking. Arrow-key navigation with wraparound, Enter to go, Escape to close. Index fetch is memoized in a module-level `indexPromise` (`:34`) that nulls itself on failure so the next open retries.

### 4.4 Storage and cross-navigation state

**There is no `localStorage` or `sessionStorage` usage anywhere in `app/`** — grep returns nothing. The *only* persistence is next-themes writing the theme key to `localStorage` internally.

The only navigation-surviving state is the URL: `?openPost=<slug>` and `?embed`.

### 4.5 What breaks with plain HTML pages and full reloads

| Behavior | Impact |
|---|---|
| Window positions, sizes, snap state, z-order | **Already lost today.** All of it lives in `useReducer` state on `/`, and every window is only reachable from `/`. Navigating away and back resets everything. A full reload changes nothing. |
| Maximize / minimize / close buttons | These are `router.push` calls. With `location.assign` they still work — they just lose the soft-nav smoothness and the view transition. |
| The `<ViewTransition>` page-change animation | **This is the real loss.** Requires same-document navigation. The cross-document `@view-transition { navigation: auto }` CSS rule gets you page-level cross-fades on full reloads in Chromium, but *not* the named element transitions (`page-blog`, `page-about`, `blog-post-<slug>`, …) that this site pairs across routes, and not in Safari/Firefox. |
| `<Link prefetch>` | Used at `widget-recent-posts.tsx:78,92` and `window-toolbar.tsx:57`. Replaceable with `<link rel="prefetch">` on hover, though you lose RSC-payload-level granularity (you'd prefetch whole HTML documents, which for a static site is fine and arguably simpler). |
| Focus | No focus restoration logic exists today. `autoFocus` on the palette input (`command-palette.tsx:119`) is per-mount. No regression. |
| Command palette across pages | Currently the palette state resets on navigation anyway (it lives in `EffectsProvider` inside the layout, which re-mounts per hard nav). The index is re-fetched, but it's a cached static JSON. Minor. |
| Theme flash | next-themes' blocking script prevents it. Any replacement must ship an equivalent inline script before first paint. |
| Scroll position | Not managed today. |
| The desktop iframe preload | Harmless either way. |

**Verdict:** the desktop is not as coupled to the Next router as it looks. The only genuine casualty of full reloads is the named view transitions.

### 5.4 Notable pipeline oddities

**`MinecraftInventoryFromDir`** (`app/components/mc/MinecraftInventoryFromDir.tsx`) recursively walks `app/components/mc/images/` at render time, base64-encodes **every PNG** into a `data:` URI (`:42-45`), and passes them all to a client component. There are **53 images** there, plus a byte-identical duplicate set of the same 53 in `public/mc/images/`. This inlines the entire image set into one page's HTML. Directory structure carries the metadata: subdirectory = mod name, filename = item name.

**GitHub stars** (`app/lib/projects.tsx:105-172`) — the project list is a hardcoded array of 11 entries. `getProjects()` is `cache()`-wrapped and:
- Throws if `GITHUB_TOKEN` is unset *and* `process.env.VERCEL` is set (`:107-111`) — so a Vercel build hard-fails without the token.
- Warns and returns unstarred data if unset in a local production build.
- In dev, fetches `http://localhost:3000/mock-stars-response.json` instead of the real API (`:132-134`), served from `public/`.
- Wraps the real fetch in `unstable_cache(..., ['projects'], {revalidate: 86400})` with `cache: 'force-cache'`.
- Catches non-JSON responses so a GitHub outage doesn't take the build down (`:151-157`).
- **`stars` is fetched and then never rendered.** `convertToProject` (`portfolio-data.ts:45-54`) drops the field entirely. This entire network dependency is currently pointless.

**`external-posts.ts`** — 6 hardcoded Vercel blog posts with `href`, `isThirdParty: true`, empty `body`, and empty `slug`. **No RSS is fetched at build**, contrary to what CLAUDE.md implies. Merged in only via `getPosts(true)` (called from `portfolio-data.ts:60`) and by the RSS script. `convertToBlogPost` uses the `href` as a pseudo-slug (`portfolio-data.ts:16`).

**`scripts/rss.mts`** — run by `pnpm build-rss`, in parallel with `next build` via `concurrently`. Node's native TS support, no bundler. Reads `posts/` and `notes/` with `gray-matter`, merges `externalPosts`, sorts by date, renders bodies to HTML with **`marked`** (gfm + breaks, custom link renderer forcing `target="_blank"`), and writes `public/feed.xml`. Two important divergences from the site renderer:
1. It uses `marked`, not the MDX pipeline — so JSX components in post bodies leak into the feed as raw text.
2. **It does not filter `published: false`.** All 30 posts and all 12 notes go into the feed, including the 11 unpublished ones. That is a real content leak.

Because it writes into `public/`, `next build` and `build-rss` race: `concurrently` runs them simultaneously, so the feed Next copies into the output may be the previous build's.

**`app/data/talks.json`** — 17 entries with `description`/`url`/`tags`. **Imported by nothing.** `talks-content.tsx:11` hardcodes a different, 18-entry `TALKS` array with a different shape. Dead file.

**`app/lib/about-content.ts`** — `ABOUT_CONTENT` is re-exported from `portfolio-data.ts:97` and **consumed by nothing**. `about-content.tsx:14` hardcodes a *different, newer* bio ("currently working on Claude Code at Anthropic" vs. the stale "currently building v0 at Vercel"). Dead file with a stale duplicate.

**`app/components/post/navigation.tsx`** — imports `./navigation.module.css`, **which does not exist**. Referenced by nothing. Dead file that would fail to compile if anything imported it.
